# 开源软件引入风险检查系统设计

> 文档类型：产品与系统设计草案  
> 文档日期：2026-10-18  
> 状态：方向设计；文中“规划能力”尚未实现

## 1. 产品概述

开源软件引入风险检查系统面向研发、平台和安全团队，用于在团队引入、升级或定期复查开源软件时，检查项目声明的第三方依赖是否命中公开漏洞，并将检查结果整理成可追溯、可审核的风险清单。

系统的核心工作是：读取项目依赖清单，识别包名和版本，查询公开漏洞数据，核对受影响版本范围，再把结果与项目中的依赖声明关联起来。评审人据此判断是否需要升级、接受风险或进一步调查。

系统提供的是依赖安全初审和决策支持。它帮助团队更快发现已公开的依赖漏洞、统一审核过程并保留依据，不承诺证明一个项目绝对安全，也不替代安全人员的最终判断。

## 2. 业务问题与目标

团队在引入开源项目或更新依赖时，通常需要人工检查多个依赖文件和外部漏洞公告。这个过程容易漏查，也容易出现结论没有证据、后续无法复盘的情况。常见的通用仓库分析报告虽然能描述项目技术组成，却不能直接回答“当前依赖版本是否受已知漏洞影响”和“接下来要处理什么”。

本方向的业务目标是：

- 将依赖清单中的声明与公开漏洞记录建立对应关系。
- 让每条风险都能回到项目依赖声明和外部公告进行核验。
- 将漏洞发现、人工审核、处理状态和报告保存为连续的工作记录。
- 显示数据不完整和无法判断的情况，避免把未知误报为安全。

## 3. 用户与使用场景

| 用户 | 主要关注点 | 系统提供的支持 |
| --- | --- | --- |
| 研发负责人或项目维护者 | 当前依赖是否需要处理、建议升级到什么版本 | 风险列表、修复信息、处理状态和项目证据 |
| 平台工程师 | 多个项目是否采用了存在已知风险的依赖 | 按项目和扫描批次查看、比较和导出风险 |
| 安全工程师或准入评审人 | 风险结论是否可信、判断依据是否完整 | 漏洞来源、版本范围、原始依赖声明和审核记录 |

典型触发时机包括：新项目或新依赖引入前、依赖升级后、周期性依赖复查，以及公开漏洞公告出现后对项目进行定向检查。

## 4. 产品范围

### 首期范围

- 输入一个 GitHub 仓库或项目依赖清单，建立一次有明确来源的扫描任务。
- 首期面向 Python 依赖，逐步支持 `requirements.txt`、`pyproject.toml` 和锁文件。
- 解析包名、生态系统、版本或版本约束，并保留原始声明和文件位置。
- 使用 OSV 等公开漏洞数据源查询已知漏洞，并按数据源提供的版本范围进行匹配。
- 提供可解释的排序、人工审核、处理状态和扫描报告。

### 明确不在首期范围

- 源代码漏洞扫描、恶意软件检测和完整的软件供应链审计。
- 判断漏洞代码是否能从当前项目实际触达，或是否在生产环境运行。
- 对许可证进行法律意见判断。
- 自动修改依赖、创建升级 PR 或阻断构建和发布。
- 将“本次没有匹配到公开漏洞”解释成“该软件没有安全风险”。

## 5. 核心业务流程

1. **创建扫描任务**：指定仓库、分支或提交，记录扫描范围和触发原因。
2. **发现依赖文件**：寻找支持的清单文件，记录文件路径、提交 SHA 和读取状态。
3. **解析依赖声明**：提取包名、生态系统、版本或版本约束，同时保存原文和位置。无法解析的条目进入待处理状态，不静默忽略。
4. **规范化与版本确认**：统一生态系统和包名格式；只有在版本能够可靠确定时才进行确定性版本匹配。
5. **查询漏洞数据**：通过 OSV API 按生态系统、包名和版本查询公开记录，记录数据源、查询时间和响应标识。[OSV API](https://google.github.io/osv.dev/api/) · [OSV 批量查询接口](https://google.github.io/osv.dev/post-v1-querybatch/)
6. **生成风险发现**：将依赖版本与公告影响范围匹配，提取漏洞编号、摘要、严重性、修复版本及公告链接。
7. **人工审核与处理**：评审人查看证据，更新处理状态并填写备注。审核动作与扫描结果关联保存。
8. **生成扫描报告**：形成该仓库和提交对应的风险快照，供团队查看、导出和后续比较。

## 6. 功能设计

### 6.1 仓库与扫描管理

每次扫描应关联仓库、目标分支或提交 SHA、发起时间、扫描状态和扫描范围。扫描结果按批次保存，使团队能回答“这份结论针对哪个版本的项目”和“后来发生了什么变化”。同一仓库的新扫描不覆盖旧快照。

### 6.2 依赖清单发现与解析

扫描器根据支持的文件类型发现依赖清单。解析器需要保留：

- 文件路径和原始依赖声明；
- 规范化后的包名与包生态系统；
- 解析出的精确版本或版本约束；
- 声明位置（行号可用时记录行号）；
- 解析状态和错误原因。

依赖来源或版本无法确认时，应作为单独状态呈现，而不是跳过后继续给出“无风险”的整体结论。版本约束无法解析成精确版本时，系统可以展示约束和待确认原因，但不应猜测实际安装版本。

### 6.3 漏洞匹配与风险排序

首期以 OSV 为公开漏洞数据来源。系统以包生态系统、包名和可确认版本作为查询和匹配条件。风险详情展示公告影响范围和数据源给出的修复版本；缺少严重性或修复版本时，应明确显示“未提供”。

排序采用可解释因素，不使用难以复核的综合分数。首期因素包括公告严重性、是否有明确修复版本，以及依赖声明是否来自运行时依赖（若清单能够区分）。用户应能看到排序依据。

系统至少区分以下结果状态：

| 状态 | 含义 |
| --- | --- |
| 命中已知漏洞 | 依赖版本符合数据源记录的受影响范围 |
| 未发现匹配记录 | 当前数据源本次查询没有返回匹配公告，不代表绝对安全 |
| 版本未确定 | 依赖约束不足以确定实际版本，无法给出确定性匹配 |
| 解析失败 | 依赖声明无法按当前支持规则解析 |
| 数据源不可用 | 查询失败或暂时无法获得漏洞数据 |

### 6.4 人工审核与处置

每条风险发现可由评审人设置处理状态，例如“待处理”“需要升级”“接受风险”“误报”或“进一步调查”，并记录处理人、时间和备注。状态变化属于审核记录，不改写上游公告内容，也不改变机器匹配结果。

首期不自动升级依赖或阻断发布。系统负责把风险与证据呈现清楚，并把审核决定留档。

### 6.5 报告与历史

报告以扫描快照为单位，至少包含仓库和提交标识、扫描时间、依赖解析概况、漏洞发现、未确定事项、证据链接及审核状态。历史页面可按仓库查看不同扫描批次，并为后续的依赖变更比较和处理跟踪提供基础。

## 7. 核心数据对象

| 数据对象 | 关键字段 | 用途 |
| --- | --- | --- |
| RepositoryScan | 仓库地址、分支、提交 SHA、扫描时间、状态 | 表示某个仓库版本的一次扫描快照 |
| DependencyRecord | 清单路径、原始声明、包名、生态系统、版本/约束、解析状态 | 保留项目依赖证据和解析结果 |
| VulnerabilityFinding | OSV ID、摘要、影响范围、严重性、修复版本、来源链接、查询时间 | 表示依赖与公开漏洞记录的匹配结果 |
| ReviewRecord | 处理状态、处理人、备注、更新时间 | 保存人工审核和处置决定 |

漏洞公告数据与审核记录应分开保存：上游数据可以更新，评审人的历史判断仍需保留。报告通过扫描批次关联依赖、发现和审核状态。

## 8. 系统架构

建议将依赖风险检查实现为一条可恢复的工作流：

```text
仓库连接器
  → 依赖文件发现
  → 清单解析器
  → 包名与版本规范化
  → OSV 数据源客户端
  → 版本范围匹配
  → 风险发现与证据存储
  → 人工审核
  → 快照报告与历史查询
```

职责划分：

- **仓库连接器**负责获取目标提交和文件内容，不负责解释漏洞。
- **解析器与规范化器**负责把依赖声明转为统一结构，并保留原始来源。
- **漏洞数据源客户端**负责请求、超时、重试、缓存和数据来源记录。
- **匹配器**负责按结构化版本范围规则匹配公告，不依赖 LLM 推断。
- **工作流引擎**承载任务状态、检查点、失败重试和人工审核暂停/恢复。
- **报告层**汇总结构化扫描结果，并提供证据跳转、筛选和导出。
- **LLM（可选）**可以把已确认字段整理成易读摘要，但不能生成或更改漏洞编号、影响范围、严重性和修复版本。

## 9. 与当前项目的关系

| 当前能力 | 可复用方式 | 当前边界 / 需要补充 |
| --- | --- | --- |
| GitHub 仓库信息与文件读取 | 作为仓库连接器和依赖清单获取基础 | 需要补充清单文件定向发现、提交版本关联和完整来源记录 |
| `DependencyAnalyzerTool` | 作为依赖分析入口的实现起点 | 当前主要读取本地 `requirements.txt`，并按关键词识别少量技术类别；尚未逐项解析版本或匹配漏洞，见 `app/analysis/tools/dependency_analyzer_tool.py` |
| Workflow 与检查点 | 承载扫描任务、重试、暂停和恢复 | 需要增加依赖扫描节点及相应的结构化状态 |
| Evidence 与报告导出 | 保存依赖位置、公告来源和审核结论 | 需要定义依赖与漏洞发现的专用字段和关联关系 |
| 前端分析界面 | 展示进度、扫描结果和历史任务 | 需要增加依赖清单、风险详情、审核操作和扫描对比视图 |

当前 RAG 索引器用于索引 Python 源码，不是漏洞数据库。漏洞是否命中及其版本范围应由结构化数据和确定性规则判断；见 `app/analysis/tools/project/rag_indexer.py`。

## 10. 非功能要求

- **可追溯**：扫描结果能回到仓库提交、依赖文件声明和外部公告。
- **可重复**：保存数据源、查询时间和扫描版本；相同输入能够解释为何得到相应结果。
- **容错**：外部数据源不可用时保留任务状态和已完成结果，支持重试，不把失败记为无风险。
- **可扩展**：解析器和漏洞数据源采用清晰接口，后续可添加其他生态系统和数据源。
- **最小化敏感信息**：首期以公开仓库为主；未来支持私有仓库时，应复用安全的凭证管理方式，避免在日志和报告中暴露令牌。
- **状态清晰**：扫描失败、部分完成、解析不确定和无匹配结果必须能够区分。

## 11. 主要风险与限制

- 漏洞数据源覆盖范围和更新时间会影响结果；报告应显示来源和查询时间。
- 版本约束、锁文件缺失和包名映射可能导致无法精确判断，应保留不确定状态。
- 严重性和是否受影响不等于项目的实际业务风险；是否可达、部署方式和补偿控制需要团队评估。
- “未发现匹配记录”仅表示指定数据源在本次查询中未返回匹配项，不构成安全保证。
- 不同包管理器的语义存在差异，新增生态系统时需要独立解析和版本范围验证。

## 12. 建设阶段

1. **依赖分析基础**：实现支持格式的依赖解析、来源定位、版本不确定状态和统一数据结构。
2. **漏洞数据与匹配**：接入 OSV，完成版本范围匹配、风险详情和失败状态处理。
3. **仓库扫描与审核闭环**：将扫描接入 GitHub 仓库和现有工作流，保存人工处理状态并生成扫描快照。
4. **持续治理能力**：增加历史扫描比较、更多锁文件和包生态，并根据实际团队需求扩展处理流程。
