# GitHub 项目分析过程 Trace 执行方案

日期：2026-10-20
状态：首版已实施，已完成本地 MySQL 迁移及自动化、浏览器验证；实施记录见第 11 节。

## 1. 目标与结论

可行。建议在当前页面右侧的运行状态下方、报告区域上方增加“分析过程”面板，实时展示系统正在执行的步骤、读取的材料、产出数量、耗时、失败和重试。

用户应能回答：

- 现在在做什么，已经做完哪些步骤？
- 正在读取哪些文件，读了多少，哪些失败？
- 是在调用 GitHub、解析代码，还是等待模型生成报告？
- 出现了什么问题，系统是否正在重试或降级？
- 是否正在等待人工确认，接下来需要做什么？

这里的 trace 记录实际执行事件与可核验的结果摘要。模型调用展示用途、开始和结束、耗时、可用的用量及错误类别；不展示模型内部思维过程，不编造“正在思考”的文字。

首版采用 **结构化事件持久化 + HTTP 增量轮询 + 可折叠时间线**。复用现有 FastAPI、MySQL 和原生前端，不增加向量库、Redis、Celery 或外部观测平台。

## 2. 当前代码中的关键约束

| 当前情况 | 方案要求 |
| --- | --- |
| `analysis_service.py` 创建 run 后等待 `start_workflow()` 执行，再把 run_id 返回前端 | 新页面需要先拿到 run_id，再启动执行，才能看到初始规划过程 |
| 批准操作会等待工作流执行到下一停顿点 | trace 请求要独立于这个长请求 |
| `app.js` 在 `state.inFlight` 时跳过状态轮询 | trace 不能复用这个跳过条件，否则最需要观察时仍无更新 |
| `PlanExecutorNode` 在一个节点内依次执行多个 Agent | 只展示节点名不足以区分仓库信息、技术栈、架构和证据阶段 |
| `output_marker()` 只记录结果类型与字段名，检查点以节点边界保存 | 不能把现有 outputs 当作完整的实时 trace |
| 主流程使用请求作用域的数据库 Session | trace 需独立短事务提交，不能等业务请求结束才可见 |
| LLM 工具可能返回 `available=false`，而不抛异常 | 要识别降级结果，不能把“没有抛异常”都标为成功 |
| 检查点已有体积控制 | trace 独立存储，不持续追加到 `state.data` 或 `outputs` |

截图显示的“执行中… design_gate”还反映了展示问题：操作开始后，页面改变了状态文字，但节点名可能仍是上一停顿点。新面板应显示真实活动事件，例如“架构分析：正在读取 src/main.py”，旧节点只作为最后确认的位置。

## 3. 页面设计

### 3.1 布局

保留现有左右布局，在右侧增加一个独立面板：

```text
运行状态
分析中 · 架构分析
已用时 00:42 · 最近活动：读取 src/main.py

分析过程                         全部 / 异常   跟随最新
✓ 获取仓库信息                    1.4 秒
  默认分支 main；README 已读取
✓ 识别技术栈                      2.1 秒
  读取 3 个配置文件
● 分析代码结构                    已用时 12 秒
  文件读取：8 / 20，成功 7，失败 1
  ▸ 查看文件明细
    ✓ src/main.py                 0.4 秒
    ✓ src/services/analysis.py    0.6 秒
    ! docs/architecture.md        读取失败，继续分析
○ 整理证据
○ 等待结果审核
○ 综合分析与报告导出

报告区域：生成完成后出现
```

示例数量与耗时仅用于说明布局，实施时必须来自真实事件。

### 3.2 交互规则

- 默认展示阶段摘要，正在运行和异常阶段展开；文件及工具调用明细按需展开。
- 阶段状态包含：待开始、执行中、已完成、部分完成、失败、重试中、等待确认、已取消。
- 状态配合文字和图标，不仅依赖颜色；沿用当前明暗主题。
- 默认跟随最新事件；用户向上滚动后停止自动滚动，显示“有新进展”入口。
- 使用事件 ID 增量更新，保留用户已展开的内容、键盘焦点和滚动位置。
- 等待人工确认时保留现有审批入口，trace 显示等待事件，不反复重建审批表单。
- 完成后自动收起过程面板，保留耗时、成功/失败文件数及异常摘要，用户可再次展开。
- 从历史记录打开任务时可以读取已保存的过程；无 trace 的旧任务显示“该任务未记录详细分析过程”。
- 手机端单列显示，不使用横向宽表；对长路径换行，完整路径支持复制。

首版提供“全部 / 异常”筛选和“跟随最新”。复杂检索、火焰图、调用图和 trace 下载不作为首版交付条件。

### 3.3 进度语义

- 整体进度展示阶段进展；没有可靠工作量分母时不展示精确百分比或固定剩余时间。
- 文件读取阶段展示真实的已处理数、计划数、成功数和失败数；计划数更新时明确同步。
- 模型等待期间展示“正在生成综合分析，已等待 35 秒”，直到收到结果或超时事件。
- “最近无新事件”“trace 连接异常”“任务失败”使用不同提示。
- 服务端心跳仅代表执行进程仍存活，不代表业务步骤有推进。
- 超过预期耗时可以提醒“该步骤耗时较长”，不能仅凭无新事件判定失败。

## 4. Trace 数据模型

### 4.1 事件字段

新增 `analysis_trace_events` 表，字段建议：

| 字段 | 用途 |
| --- | --- |
| `event_id` | 客户端去重的稳定唯一标识 |
| `run_id` | 所属分析任务 |
| `sequence` | 同一 run 内单调递增的读取游标 |
| `execution_id` | 一次启动、继续、重新规划或重试的执行批次 |
| `span_id`、`parent_span_id` | 关联节点、Agent、Skill、工具及文件操作 |
| `event_type` | 例如 `span.started`、`span.finished`、`span.failed`、`retry.scheduled` |
| `category` | `run / node / agent / skill / tool / file / llm` |
| `name`、`message` | 稳定机器名称及可读摘要 |
| `status`、`level` | 执行结果、信息或警告级别 |
| `occurred_at` | UTC 时间，页面按本地时区显示 |
| `duration_ms` | 完成事件的实际耗时 |
| `attributes` | 白名单 JSON：路径、数量、重试次数、错误类别等 |

索引包含 `(run_id, sequence)` 唯一索引，以及 `(run_id, execution_id, span_id)` 查询索引。

每个操作的开始和结束使用相同的 span_id；重试创建新的尝试 span，并记录 attempt，保留之前的失败事件。运行耗时使用单调时钟计算，时间展示使用 UTC 时间戳。

### 4.2 提交与排序

- 在组合根注入 TraceRecorder，通过接口或可选上下文能力提供给执行组件；通用工作流不直接依赖 SQLAlchemy。
- 使用独立 Session 和短事务写入事件，避免跟随主业务事务延迟提交或一起回滚。
- 增加轻量的 `analysis_trace_streams` 表，按 run 维护 `last_sequence`。事件写入事务锁定对应 stream 行、分配序号、插入事件并一起提交。
- 不直接以自增主键作为消费游标：并发事务可能先分配较小 ID、后提交，导致客户端永久跳过该事件。
- 不在 trace 事务中更新主业务 run 行；trace 表首版以应用层校验 run_id，不加指向可能被长事务锁住的 run 行的外键，避免独立写入反而等待主流程。
- 删除任务时由服务层一并清理对应 stream 和事件，不创建孤立记录。
- 查询接口每次使用短读事务；不能持有长事务持续轮询而读到旧快照。

### 4.3 内容与故障边界

- 记录路径、数量、耗时和结果摘要；不保存 API 密钥、请求头、完整源码、完整 prompt 或模型原始输出。
- 错误仅保存经过脱敏的类别和摘要；完整服务端堆栈保留在原日志中，并附 run_id/execution_id 便于定位。
- GitHub 内容视为普通文本显示，前端使用安全文本渲染；文件链接校验协议和来源。
- 每条事件载荷建议最多 4 KB；文件操作聚合到同一行，按页加载历史，避免无限增加 DOM。
- trace 写入超时或失败不改变分析结果，不无限重试；记录服务端告警，后续恢复时报告存在事件缺口。
- 健康状态查询与事件数据分开返回，trace 故障时页面明确提示记录可能不完整。
- 初始保留期建议 30 天；清理只针对已经结束且超过保留期的任务事件。旧报告本身不随 trace 清理而删除。

## 5. 后端采集位置

| 层级 | 主要位置 | 记录内容 |
| --- | --- | --- |
| 生命周期 | `analysis_service.py`、`analysis/workflow.py` | 创建、开始、批准、继续、重新规划、重试、暂停、取消及最终结果 |
| Workflow | `workflow/engine.py` | 节点开始、结束、异常、重试等待及人工闸门 |
| Agent | `plan_executor_node.py`、`agent_node.py` | 当前 Agent、顺序、耗时及结果数量摘要 |
| Skill | `generic_skill_agent.py` 及直接调用 Skill 的节点 | 技能开始、结束、降级结果 |
| 文件与材料 | 架构、仓库、技术栈技能 | 实际选取数量、文件读取进度、解析成功/失败、文档及配置采集 |
| GitHub 工具 | `file_reader_tool.py`、仓库工具 | 请求用途、路径、耗时、API 回退和限流/超时 |
| LLM | `integrations/llm/chat_tool.py` | 调用用途、模型名、耗时、可用用量、超时、不可用或解析失败 |
| 报告 | `synthesis_node.py`、`finalizer_node.py` | 综合开始、来源整理、导出格式、导出成功/失败 |

节点负责节点 span，Agent/Skill 负责各自层级，工具负责 I/O；同一次文件读取不由多个位置重复生成同类开始事件。父子关系通过显式上下文或 ContextVar 传递，必须在 finally 中恢复，避免并发任务串 run。

`available=false`、部分文件读取失败、返回空材料等情况生成 `partial/unavailable` 结果或警告，不能只根据是否抛异常决定显示成功。

实际工作流顺序包括设计审核、计划执行、结果审核、综合分析和导出。前端按照运行事件构建时间线，不假定每次都经过固定数量的 Agent。

## 6. 接口与执行方式

### 6.1 获取事件

新增：

```http
GET /api/v1/analysis/{run_id}/trace?after=0&limit=100
```

返回建议：

```json
{
  "run_id": "example",
  "events": [],
  "next_cursor": 42,
  "has_more": false,
  "trace_state": "available",
  "execution": {
    "execution_id": "example-execution",
    "status": "running",
    "current_stage": "architecture_analysis",
    "last_activity_at": "2026-10-20T08:00:00Z"
  }
}
```

`next_cursor` 来自实际返回的最后一条事件；空结果保持原游标。明确区分可用、旧任务无记录、已过期和暂时不可用。`has_more=true` 时继续追赶，不等待下一轮正常轮询。

普通查询默认 limit=100，最大 200。不存在的 run 返回 404；按现有任务访问策略校验权限，后续接入用户系统时须与任务详情使用同一所有权校验。

### 6.2 先获得 run_id，再启动分析

首版采用最小执行方式调整：

1. 为现有创建接口增加显式 `defer_start=true` 选项。新页面使用该选项，仅创建并提交 run 和初始输入，立即获得 run_id。
2. 初始输入写入可恢复的初始检查点，run 标记为 CREATED。
3. 页面保存 run_id、更新地址并启动 trace 轮询。
4. 新增 `POST /analysis/{run_id}/start`，从已保存的输入启动工作流。
5. 原创建接口默认行为保留，旧客户端仍可等待工作流执行后取得结果。

`start` 和原有 approve/resume/retry 等请求在首版仍等待工作流到达下一停顿点。页面发出操作请求后，trace 的独立请求可以继续执行。这样无需同时引入后台任务队列。

必须同时处理：

- 同一 run 的 start/approve/resume/retry/replan 使用统一执行互斥，不能只靠前端禁用按钮；多进程部署也要有效。
- 可用 MySQL 命名锁实现首版互斥，由专用连接持有、finally 释放，并校验执行前置状态；锁连接丢失时停止该执行，不允许失去锁后继续写结果。
- 同 run 的重复执行请求返回明确的 409 或当前执行信息；完成后的 start 不重复执行。
- trace 请求不争抢执行锁。
- 首版沿用长请求的执行生命周期，不承诺关闭页面后一定继续运行；页面刷新后先查询任务、检查点与当前执行是否仍有效，禁止自动重复 start。
- 请求超时不直接等于执行失败；重连后先查询状态。服务进程中断时显示“执行状态待确认/执行已中断”，不伪造完成事件。
- pause/cancel 的实际生效时机遵循执行器安全边界，区分请求已接收和已经停止；不承诺立即终止正在进行的外部请求。

如果后续要求关闭页面后可靠运行、重启自动恢复、多任务排队，则单独设计持久化任务调度。仅使用 `asyncio.create_task()` 不应被当作可靠后台执行方案。

## 7. 前端刷新与恢复

- 将 trace 的游标、轮询器、请求 AbortController 与原任务状态轮询分开管理。
- 分析进行中建议约 1 秒增量查询一次，使用完成后再 setTimeout 的方式，避免请求重叠。
- 人工操作 `inFlight` 时继续获取 trace；原审批按钮仍保持禁用，不因旧 WAITING 状态重复出现。
- 等待人工确认后降低刷新频率；操作开始立即恢复；任务终态追赶剩余事件后停止。
- 对数据库状态更新和事件提交之间的短暂差异，以最后确认的执行状态协调展示，终态不能仅靠收到某个子步骤完成事件判断。
- 网络失败采用退避重试并提示连接状态；切换 run 时取消旧请求，校验响应对应的 run_id，避免旧结果写入新任务面板。
- 页面隐藏时降低频率，重新可见时立即追赶；游标按任务隔离。
- 初次打开或刷新时分页加载记录并重建 span；事件重复投递时按 event_id 去重。
- 长历史只保留有上限的可见节点，提供加载更早记录，不一次性渲染全部事件。

SSE 可作为后续优化，复用同一事件存储和游标。首版不需要同时实现轮询、SSE 与 WebSocket。

## 9. 实施阶段与完成标准

### 阶段一：事件基础与执行接入

1. 定义 schema、状态语义、游标及脱敏规则。
2. 完成两张表与迁移、独立短事务写入、分页查询。
3. 注入可选 TraceRecorder，接入生命周期和节点事件。
4. 实施先创建后启动及统一执行互斥。

完成标准：run_id 立即可获得；初始规划和批准后的长执行均能在结束前查询到事件；不开 trace 时原业务仍可运行。

### 阶段二：业务细节与页面

1. 增加 Agent、Skill、文件读取、模型调用和导出事件。
2. 增加时间线、摘要、展开、筛选和跟随最新。
3. 修正操作在途时节点名滞后问题，保留审批交互状态。
4. 实现历史加载、刷新恢复和断线追赶。

完成标准：截图中的空白区域可以显示真实过程，用户能看到具体文件、模型等待及异常；刷新后能恢复同一任务的过程。

### 阶段三：故障验证与交付

1. 覆盖正常、部分失败、重试、等待审核、取消及进程中断。
2. 检查多任务隔离、并发游标、任务重复执行和数据库锁等待。
3. 验证事件写入故障不会中断报告流程；明确显示记录缺口。
4. 完成桌面与手机、明暗主题验证，记录真实开销。
5. 更新使用文档和迁移说明，交付可重复的验收结果。

## 10. 验收清单

- [ ] 创建任务后、Planner 完成前，页面已经显示该任务的真实事件。
- [ ] approve 请求尚未返回时，文件读取与 Agent 事件持续更新。
- [ ] 至少一条进行中事件在对应慢步骤结束前可见。
- [ ] 正常环境下事件提交后约 2 秒内出现在页面；这是验收目标，不是已测性能。
- [ ] 文件统计与实际采集结果一致，不用定时器生成假进度。
- [ ] 模型不可用、读取部分失败明确显示降级，仍能继续生成报告。
- [ ] 同 run 重复提交不会导致重复执行；不同 run 的事件不混淆。
- [ ] 并发提交、重连和分页追赶不会跳过或重复显示事件。
- [ ] trace 独立事务不会等待主流程长事务结束才提交。

- 实现重新连接、游标去重、页面刷新恢复、明暗主题和手机布局；每次最多渲染 250 个操作 DOM，已加载的摘要可翻看更早记录。
